# F6.4 — threat note

**Feature.** The "open them sandboxed" half of FR-18 and the first clause of docs/06 §6: a
`Bundle` artifact is rendered with **no same-origin relationship to the control UI**, under
a restrictive CSP, with no network and no host access. A new authenticated jarvisd route
serves the app *document*; the Angular shell renders it in a script-sandboxed frame.
Records **ADR-030**.

**Trust zones touched.** Z0 (jarvisd) and the **control UI's own origin** — the most
privileged surface in the browser, holding the device token. The new thing in this feature
is not a process; it is a *rendering* of untrusted, model-influenced code inside the user's
browser. Everything below is about which origin that code ends up in.

**Risk tiers.** None directly: rendering performs no tool call. The bridge that lets a
rendered app *ask* for one is F6.5, and it does not exist yet — an app rendered today can
only draw.

**Threats considered.**

1. *Same-origin escape — the whole feature.* If the bundle ran in the control origin it
   could read the device token, call every `/api/v1` route as the user, and rewrite the
   HUD. Two independent mechanisms prevent it, and neither is a header the document could
   influence: the frame carries `sandbox="allow-scripts"` **without** `allow-same-origin`,
   which gives the document a unique opaque origin; and the route's response carries
   `Content-Security-Policy: sandbox …`, which forces an opaque origin even for a direct
   navigation that never went through the shell.
2. *One-token regression.* Adding `allow-same-origin` to that attribute — a plausible
   "fix" for an app that cannot reach `localStorage` — collapses mechanism 1 entirely, and
   in combination with `allow-scripts` lets the frame remove its own sandbox. This is the
   single most likely way this feature is destroyed later, so the exact token set is
   asserted by a test that names the reason, not just the value.
3. *Untrusted bytes rendered into the privileged document.* The shell fetches the app
   document with the device token and hands it to the frame. Handing it to anything else —
   `innerHTML`, a template interpolation, Angular's HTML sanitizer path — would place
   model-influenced markup in the control origin. The renderer therefore takes exactly one
   route (`srcdoc` on a sandboxed frame) and a test asserts the bytes are never bound
   anywhere else.
4. *Network egress from a rendered app.* `default-src 'none'` with `connect-src 'none'`
   and `form-action 'none'` means the document may not fetch, XHR, WebSocket, submit or
   navigate anything anywhere — a rendered app cannot phone home even though its content
   came from a model. `img-src`/`font-src` allow `data:` only, so nothing loads off-box.
   The F6.2 build-time refusal of external subresources is the same rule enforced one step
   earlier; this is the one that actually binds at render time.
5. *The bundle route weakening the blob route.* M3a deliberately serves artifact blobs as
   `attachment` + `nosniff` so they are never rendered inline (security-auditor B1). The
   app document is a **separate route**; the blob route is untouched, and a test asserts
   both — the app route renders, the blob route still downloads, including for the same
   `Bundle` artifact.
6. *Serving a non-bundle through the render path.* If any artifact kind could be fetched
   as an app document, a `text/markdown` note whose bytes came from a fetched web page
   would suddenly be executable content. The route requires `kind == Bundle` and refuses
   everything else, which is the server-side half of "every kind has exactly one render
   path".
7. *Direct navigation to the app document.* The route sits behind the bearer middleware,
   so a browser navigation (which cannot set `Authorization`) gets a 401, not a document.
   Mechanism 1's `Content-Security-Policy: sandbox` covers the case anyway.
8. *`'unsafe-inline'` for script.* The single-file bundle is one inline module script, so
   the policy must permit inline script or nothing renders. This is not a weakening: the
   entire document is the untrusted unit, and permitting the app's own script to run is
   the point of rendering it. What the policy denies is everything that would let that
   script *reach* anything — origin, network, form, base URI, plugins.

**User-visible failure states.** A non-bundle artifact requested as an app is a 404. A
bundle over the served cap is the same typed 413 F6.3 introduced. A bundle whose blob fails
integrity is the existing fail-closed 500 with no bytes.

**Invariants.** 1 — rendering grants nothing; there is still no path from bundle content to
a side effect, and F6.5 will add one only through `policy::evaluate`. 3 — the render
decision is a domain predicate (`ArtifactKind::renders_in_app_sandbox`), not an ad-hoc
check in a handler. 5 — the app document is served to an authenticated device only, and the
frame it lands in cannot read the token that fetched it.
