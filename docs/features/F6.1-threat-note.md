# F6.1 — threat note

**Feature.** App spec format, closed capability vocabulary, bundle manifest contracts
(FR-18, docs/06 §6, ADR-029). Pure domain + contracts; no new I/O, no new process, no new
network surface, no new dependency.

**Trust zones touched.** Z4 → Z0 only. The app spec is **model output** (Z4, docs/06 §2)
crossing into the core-authority zone as *data*. Nothing in this feature executes, builds,
fetches or persists anything: `AppSpec::validate` is a pure function, and its output is a
value object.

**Risk tiers involved.** None directly — no tool is registered, proposed or executed here.
Indirectly the feature *defines* the tiers a generated app may later reach: R0
(`home.read_state`), R1 (`home.set_light`), R2 (`home.execute_scene`). `Capability::risk()`
is a **preview** for approval text; the authoritative decision stays `policy::evaluate`
against the live registry, and a `jarvisd` test asserts the preview never diverges from the
registered tool's host-owned `ToolPolicy.risk`.

**Threats considered.**

1. *A model invents a capability and the bridge honours it.* Closed by construction: the
   vocabulary is an exhaustive enum, an unknown name is a typed rejection at validation
   time, and the wire type for a manifest's capabilities is the closed union.
2. *A spec declares one thing and the app renders another.* `UndeclaredBindingCapability`:
   a binding may only draw on a capability the spec declared, so the manifest can never
   under-describe the app the bundle contains.
3. *Rejection messages as an injection/spoofing channel.* Every error variant that quotes
   model-authored text (`template`, capability, title, binding name/target) routes it
   through `echo_untrusted` — the F2.8/CF-13 sanitizer — clamped to 64 bytes with control
   and bidi/zero-width characters stripped. Asserted directly by two tests.
4. *Resource exhaustion before any structural check.* Size is the first gate
   (`MAX_APP_SPEC_BYTES`), and cardinality is checked before per-item parsing, so a hostile
   spec cannot force 10,000 parses to learn it was too long.
5. *A spec buying itself a bigger budget.* Limits are host ceilings; a request above one is
   **rejected, not clamped**, so a caller never receives a build under a limit it did not
   choose.
6. *Silent authority drift from stored data.* A persisted capability string outside the
   vocabulary now fails the manifest load (fail closed) rather than being dropped from the
   list, which would have made an app look *less* capable than its bundle. Covered by a
   live-Postgres test.

**User-visible failure states.** An invalid spec produces a typed `AppSpecError` naming the
one thing that was wrong (unknown template, unknown capability, oversized, duplicate,
undeclared binding capability, bad title/name/target, limit above ceiling or zero). All are
safe to render and to audit. No partial state exists: validation is total and produces
either a whole `AppSpec` or nothing.

**Invariants.** 1 (text never grants authority) — the whole feature; a spec is a *request
to ask*, never authority. 3 (domain purity) — `jarvis-domain` gains no dependency;
`arch-test` unchanged. 5 (no secrets) — no secret-shaped field exists in a spec, and echoes
are sanitized. 6 (append-only audit) — untouched.
