# F6.3 — threat note

**Feature.** Streaming, size-capped blob read (closes **CF-M3a-A**). `BlobStore::get`
returns `Vec<u8>` and `GET …/versions/{v}/blob` buffers the whole artifact with no
served-size cap. Markdown notes and patches were small; M6 `Bundle` artifacts are not.

**Trust zones touched.** Z0 (jarvisd) ↔ local filesystem. No new external surface, no new
process, no new network egress. The bytes served are already-authenticated reads of
content-addressed blobs; nothing about *who* may read changes.

**Risk tiers involved.** None — this is a read path already reachable by an authenticated
client, not a tool.

**Threats considered.**

1. *Memory exhaustion by artifact size (the actual CF-M3a-A risk).* A single large bundle
   currently becomes a full in-memory `Vec<u8>` per concurrent request on an 8 GB ultrabook
   (NFR-15, docs/09 §5). Streaming replaces peak-equal-to-blob-size with a bounded chunk
   buffer, and a **served-size cap** bounds the total regardless.
2. *Integrity silently dropped in the name of streaming.* Verify-on-read today re-hashes the
   buffered blob; the naive streaming fix deletes the check. It must not. The design is
   **chunked-hash-then-emit**: hash as chunks are read, and never let a caller observe a
   completed body whose hash did not match. This is the finding most likely to be
   introduced by a careless implementation, so it gets an explicit test with a tampered
   blob larger than one chunk.
3. *Partial-body confusion.* If verification fails mid-stream, the client has already
   received bytes and HTTP cannot retract them. The response must fail in a way a client
   can detect (abort the body rather than terminate it cleanly), and the failure must be
   logged and observable server-side. A truncated body that looks complete would be the
   worst outcome — worse than the current buffering.
4. *Cap bypass via range requests or `If-None-Match`.* The cap and the verification must not
   be skippable through a conditional or partial request path.
5. *Anti-execution guarantees must survive.* `nosniff` + `Content-Disposition: attachment`
   on the existing blob route are a deliberate M3a control (security-auditor B1) and must
   remain exactly as they are. F6.4 adds a *separate* renderable bundle route; this feature
   does not weaken the existing one to get there.

**User-visible failure states.** A blob over the served cap is refused with a typed problem
body rather than a partial download. A blob failing integrity produces the existing
fail-closed error (no bytes for a fully-buffered small blob; an aborted body for a large
one). A missing blob stays a 404.

**Invariants.** 3 (domain purity) — the new read shape is a port signature in
`jarvis-application::ports`, implemented in infra; no domain dependency changes.
4 (cancellable) — a streamed read must observe cancellation/client disconnect and stop
reading, not run to completion for a gone client. 5 (no secrets) — unchanged; error
messages carry no paths.
