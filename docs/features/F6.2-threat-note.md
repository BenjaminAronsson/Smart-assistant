# F6.2 — threat note

**Feature.** The sandboxed **app builder**: `tools/app-builder` (a Node worker that renders
a validated [`AppSpec`](../../crates/jarvis-domain/src/appspec.rs) against a locked Vite
template and returns one self-contained document) plus `jarvis-adapters::app_builder` (the
host that owns the policy, the caps, the provenance, and the artifact write). Third
instance of the worker pattern shipped in F3a.5/F3a.6 — not a new execution primitive.

**Trust zones touched.** Z0 (jarvisd) ↔ **Z4 (the builder worker and everything it runs)**.
The worker executes third-party build tooling over a dependency tree; it is the least
trusted process the system spawns, and it is the *only* new one here. The spec it is given
is model-authored, but has already passed total domain validation (F6.1) — so the worker
receives a closed template id, a closed capability set, length-capped names and
host-ceilinged limits, never free text that could steer a build.

**Risk tiers.** The build itself is host-owned `ToolPolicy` — **R1, local egress, no
grant**: producing a bundle is *data output*, exactly like F3a.6's patch. The bundle can do
nothing on its own; authority to *act* is a separate question answered by the F6.5 bridge,
against `policy::evaluate` and a real `ExecutionGrant`. Building is not authorizing.

**Threats considered.**

1. *The worker lies about its own isolation.* A compromised worker that could self-report
   `network: disabled` would launder exactly the provenance docs/06 §6 exists to record.
   **Build provenance is host/ops-attested** — the host is constructed with the true
   posture of the launch profile it drove and ignores any provenance-shaped field in a
   worker reply (same rule as `coding.rs`; docs/06 §5/§6). A `BuildNetwork::Disabled`
   claim is only ever produced by a host that launched a network-isolated profile.
2. *The bundle is model-influenced content that will later be rendered.* This is the
   feature's sharpest edge, and the reason the output shape is **one self-contained
   document**: no archive, therefore no extraction, therefore no path traversal, no
   zip-slip, no decompression bomb, and no multi-file origin surface for F6.4 to police.
   The host additionally refuses a bundle carrying an **external subresource reference**
   (`http:`, `https:`, or scheme-relative `//` in the document), because a self-contained
   document has no legitimate reason to hold one. That check is defence in depth and
   fails the *build*; the enforcement that actually matters is F6.4's CSP at render time,
   and this note does not pretend otherwise.
3. *Resource exhaustion — the real one.* A Node build is the heaviest thing this system
   spawns (docs/09 §5, 8 GB target). Bounded on **both** sides and at **three** levels:
   the worker kills its own build at the spec's `maxBuildSeconds`; the host bounds the
   whole round trip independently (a wedged worker cannot hang a run — invariant 4); and
   the returned bundle is capped at `min(spec limit, host ceiling)` with the host, not the
   worker, deciding. An over-cap bundle is refused, never truncated: a prefix of a bundle
   is not a bundle.
4. *A newline-less flood on the worker's stdout.* The line protocol is bounded by
   `MAX_WORKER_LINE_BYTES`, so an untrusted worker cannot OOM the host by never sending a
   `\n` (docs/06 §5, the discipline F3a.5 established).
5. *Secrets leaking through the worker.* The worker inherits the host environment, so its
   child's **stderr may carry a credential**; the worker therefore never forwards raw
   child stderr, and the host sanitizes and length-caps every diagnostic before it reaches
   a log, span, audit reason or model prompt (invariant 5). The builder needs no
   credential of its own and is given none.
6. *Protocol desync pairing a build with the wrong reply.* The exchange carries no echoed
   id, so an exchange interrupted after the request is sent would desync the next one. The
   transport **poisons itself** and fails closed instead (invariants 4/6) — the rule
   F3a.5/F3a.6 already follow.
7. *An un-audited artifact.* The manifest and its `artifact.created` audit event are
   written in one transaction (invariant 6). A build whose provenance or audit cannot be
   recorded produces **no artifact**; there is no path that stores bundle bytes and
   reconciles the record afterwards.
8. *Spec text reaching generated source as code.* The worker never interpolates spec
   values into source. The validated spec is written as a **`spec.json` data file** the
   locked template imports; a binding name is an identifier by construction (F6.1) and a
   binding target is opaque, carried and never interpreted. There is no `eval`, no
   template-string splice, and no host-side HTML assembly.

**User-visible failure states.** A build that exceeds its time or size budget fails with a
typed error and no artifact. A worker that dies, desyncs or returns a malformed reply is a
typed protocol failure, not a hang. A cancelled run mints nothing.

**Invariants.** 1 — the worker proposes bytes, never actions; the bundle's *capabilities*
come from the host-validated spec, not from anything the worker says. 3 — the adapter
depends only on application ports. 4 — the round trip takes a `CancellationToken`,
cancellation is checked again before the persist phase, and the timeout is host-owned.
5 — no secret is passed to the builder and no raw child output is echoed. 6 — artifact and
audit are one transaction.

**Deviation recorded here (D-M6-1).** The **production container launch profile** for the
app builder is deferred, exactly as D-M3a-2 deferred it for the browser worker; ADR-027's
process + profile-dir fallback is what ships. The consequence is made honest rather than
papered over: in the fallback the host records `BuildNetwork::Enabled`, because that is
what is true. `Disabled` is reserved for a launch profile that actually isolates the
network.
