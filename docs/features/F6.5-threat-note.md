# F6.5 — threat note

**Feature.** The **capability bridge**: docs/06 §6 clause 2 — *"optional interaction only via
a `postMessage` bridge exchanging short-lived capability tokens for operations named in the
artifact manifest; undeclared capability ⇒ reject."* Domain token types, an application-layer
`AppBridge` use case, two jarvisd routes, the shell's forwarder, and the app-side client in
the locked template. Also closes **D-M5-4**.

**Trust zones touched.** Z4 (a generated app, the least trusted thing in the system) now has
a path — a narrow, gated, audited one — to Z0's tool executors. This is the only feature in
M6 that creates authority rather than restricting it, and it is the sharpest test invariant 1
has faced: model-authored content asking for a physical effect.

**Risk tiers.** All of them the vocabulary spans: R0 (`home.read_state`), R1
(`home.set_light`), R2 (`home.execute_scene`, approval + grant). Deliberately, so the bridge
exercises the auto-authorized, live-shown and approval+grant paths rather than only the easy
one.

**The load-bearing claim.** *Naming is not authorizing.* A capability token buys the right to
be **evaluated**, never the right to execute. After the two bridge gates, the request takes
the identical path a model-proposed tool call takes — `policy::evaluate` against the live
registry, approval where the tier demands it, a real `ExecutionGrant` minted, validated and
consumed for R2+, execution, audit — with nothing removed from it.

**Threats considered.**

1. *An app asks for a capability it never declared.* The manifest is the authority, and it is
   checked at **both** ends: at mint (so an honest app is refused at the first step) and at
   exchange (so a token that should not exist still buys nothing). Rejection is audited as
   `app.capability_denied` — golden 8 asserts on that row, because a rejection nobody can
   observe is indistinguishable from an absent check. Decidable only because ADR-029 closed
   the vocabulary: a bridge enforcing free-form strings enforces nothing.
2. *A token is replayed.* `consume` **is** the lookup — it removes — so single use is the
   only operation available and there is no separate replay check to forget. A token that
   fails a binding is spent anyway: an attacker gets one probe per token, never an oracle.
3. *A token is forged, stolen, or borrowed from another app.* Every field of the token is a
   binding, and all of them are checked: artifact, version, capability, device, deadline.
   Two apps open at once cannot use each other's tokens, and a token cannot cross to another
   device or survive into a new version of the same app. An unknown token and a spent one
   report the *same* reason so a caller cannot probe the token space.
4. *A message names arbitrary tool arguments.* It cannot: the host builds the argument tree
   from the closed capability plus one validated target and (where the operation takes one)
   one validated value. There is no field on the wire for a tool id, an argument name, a
   count, or a nested structure.
5. *A valid-looking target reaches a resource the owner never authorized.* Validity is not
   authority. The target goes through the **same** domain validation an app spec's binding
   target does — the identical function, so a looser second check cannot open a hole in the
   first — and the backing tool then re-resolves it through its own entity allowlist, exactly
   as it would for any other caller.
6. *An app escalates past its owner.* The bridge passes the **device's own scopes** to
   `policy::evaluate` and widens nothing, so an app can never reach a tool whose scope its
   owner's session lacks.
7. *The declared tier is used as the decision.* It is not. `Capability::risk()` is a display
   preview (ADR-029 §4); the live registry decides, and a test registers a read tool at R2 to
   prove the bridge demands approval even though the capability advertises R0. If that ever
   inverted, an app's own manifest would be choosing its authorization level.
8. *The bridge is spoofed by another window.* An opaque-origin frame posts with
   `origin === "null"`, which every sandboxed frame shares, so origin comparison proves
   nothing (ADR-030 recorded this consequence in advance). The shell accepts a message only
   when `event.source` **is** this frame's `contentWindow`, and ignores everything else
   silently — a page cannot learn whether an app is open by probing. Outbound,
   `targetOrigin: '*'` is required because an opaque origin has no name; it is bounded by
   posting only into that one frame and only a reply envelope.
9. *A refusal leaks.* Only a stable machine code crosses back into the app — never a
   server-authored sentence, which a generated app could render as if the shell had said it.
10. *A credential in the app.* There is none. The app holds no token and has
    `connect-src 'none'`; the shell, which does hold the device token, makes every call. So
    there is nothing in the frame to steal, and every bridge call is attributable to a paired
    device.
11. *An un-answerable effect (**D-M5-4**).* Through M5 a `tool.executed` audit row named only
    the tool: the append-only trail could say *that* `home.set_light` ran and never *which
    light*. Both the orchestrator and the bridge now bind `sha256(canonical_form(args))` into
    the row — the **same function** the grant table binds, pinned by an infra test, so an
    audit row and a grant row for one effect carry the same value and can be joined. The
    arguments themselves are still never stored (invariant 5).

**User-visible failure states.** A refused capability leaves the app's card empty with a
machine code; the app keeps working. An unapproved R2 operation simply does not happen. A
timed-out request resolves as a refusal rather than hanging a card forever.

**Invariants.** 1 — there is no path from a bridge message to a side effect that does not
pass `policy::evaluate` and, for R2+, mint and consume a real grant. 3 — the bridge is an
application use case over ports; token randomness and the SHA-256 digest are infra. 4 — the
exchange takes a `CancellationToken` and uses the orchestrator's own race helper. 5 — token
ids never render in `Debug`, arguments never enter an audit payload, and no diagnostic
crosses back into the app. 6 — every refusal and every execution is an audit row.
